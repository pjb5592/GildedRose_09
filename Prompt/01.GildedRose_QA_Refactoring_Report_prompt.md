**Cursor**

요청하신 `.cursorrules`용 규칙 텍스트를 만들기 전에, Cursor 규칙 작성 방식에 맞추기 위해 관련 스킬 내용을 먼저 확인하겠습니다.

아래 내용을 프로젝트 루트의 `.cursorrules`에 그대로 붙여넣으면 됩니다.

```text
# Gilded Rose C++17 프로젝트 규칙

## 역할
- 이 프로젝트에서는 레거시 코드 QA와 안전한 리팩토링을 돕는 시니어 C++ 엔지니어처럼 행동한다.
- 기존 동작을 보존하는 것을 최우선으로 하며, 변경 전후의 테스트 결과를 반드시 확인한다.

## 기술 스택
- 언어 표준은 C++17을 사용한다.
- 빌드 시스템은 CMake를 사용한다.
- 테스트는 Google Test를 사용한다.
- 커버리지는 필요 시 gcov/lcov 기준으로 확인한다.

## 절대 규칙
- `Item` 구조체의 필드, 생성자, public 인터페이스를 수정하지 않는다.
- 일반 아이템의 `quality`는 항상 0 이상 50 이하를 유지해야 한다.
- `Sulfuras`는 예외이며 `quality`가 변경되지 않는다.
- `sellIn`은 음수가 될 수 있으며, 음수 상태를 오류로 취급하지 않는다.
- 기존 요구사항을 모호하게 바꾸거나 암묵적으로 확장하지 않는다.

## 테스트 규칙
- 기능 변경 또는 리팩토링 전에는 현재 테스트가 Green인지 먼저 확인한다.
- 새 테스트는 Given-When-Then 흐름이 드러나도록 작성한다.
- Google Test에서는 관련 테스트 픽스처를 사용하고 `TEST_F`를 우선 사용한다.
- 경계값 테스트를 반드시 고려한다:
  - `quality == 0`
  - `quality == 50`
  - `sellIn == 0`
  - `sellIn == -1`
- 테스트 이름은 동작과 기대 결과가 명확히 드러나게 작성한다.
- 버그 수정 전에는 가능하면 실패하는 테스트를 먼저 추가한다.

## 리팩토링 규칙
- 리팩토링은 테스트가 Green인 상태에서만 진행한다.
- 리팩토링 중에도 작은 단위로 변경하고 자주 테스트를 실행한다.
- 동작 변경과 구조 개선을 한 번에 섞지 않는다.
- 매직 넘버는 의미 있는 상수로 추출하는 것을 권장한다.
  - 예: `0`, `50`, 품질 증가/감소량, 특별 아이템 이름 등
- 중복 제거는 허용하되, Gilded Rose 규칙의 가독성을 해치지 않아야 한다.
- 레거시 코드의 특수 케이스를 제거하거나 일반화하기 전에 반드시 테스트로 보호한다.

## 코드 작성 기준
- 기존 코드 스타일과 파일 구조를 우선 따른다.
- 불필요한 추상화나 과도한 설계를 추가하지 않는다.
- 조건문을 정리할 때는 아이템별 비즈니스 규칙이 명확히 보이도록 한다.
- 주석은 복잡한 도메인 규칙을 설명할 때만 간결하게 작성한다.

## 작업 완료 기준
- 변경 후 관련 Google Test를 실행한다.
- 가능하면 전체 테스트도 실행한다.
- 테스트 실패가 있으면 리팩토링을 멈추고 원인을 먼저 해결한다.
```

테스트 디렉터리에는 현재 `GildedRoseTest.cpp`만 실제로 존재하며, 기본 실패 테스트가 남아 있습니다. 보고서에는 이 상태도 QA 관점의 개선 필요사항으로 정리하겠습니다.

보고서에 실제 검증 결과를 넣기 위해 현재 테스트 실행 가능 여부를 확인하겠습니다. 기존 빌드 산출물 위치가 README와 다를 수 있어 CMake 빌드 폴더 상태를 먼저 확인합니다.

테스트 실행 결과 현재 `GildedRoseTest.Foo`가 의도적인 `fixme` 기대값 때문에 실패합니다. 보고서에는 이 실패를 현황으로 기록하고, 다음 단계로 테스트 보강과 리팩토링 순서를 제안하겠습니다.

이제 `Report` 폴더에 Markdown 보고서를 생성합니다. 프로젝트 요구사항, 현재 코드/테스트 상태, QA 관점 리스크, 테스트 및 리팩토링 권장 순서를 한 문서에 정리하겠습니다.

`Report/GildedRose_QA_Refactoring_Report.md` 보고서를 생성했습니다.

보고서에는 프로젝트 개요, 절대 준수 규칙, 현재 코드/테스트 상태, 테스트 보강 항목, 리팩토링 권장 순서, 주요 리스크를 정리했습니다.

검증도 함께 실행했습니다: 빌드는 성공했지만 현재 `GildedRoseTest.Foo`가 `"fixme"` 기대값 때문에 실패합니다. 이 내용도 보고서에 반영했습니다.
