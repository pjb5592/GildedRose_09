- 언어 표준은 C++17을 사용한다.

- 테스트는 Google Test를 사용한다.

- `Item` 구조체의 필드, 생성자, public 인터페이스를 수정하지 않는다.

- `sellIn`은 음수가 될 수 있으며, 음수 상태를 오류로 취급하지 않는다.
- 기존 요구사항을 모호하게 바꾸거나 암묵적으로 확장하지 않는다.

## 테스트 규칙
- 기능 변경 또는 리팩토링 전에는 현재 테스트가 Green인지 먼저 확인한다.
- 새 테스트는 Given-When-Then 흐름이 드러나도록 작성한다.
- Google Test에서는 관련 테스트 픽스처를 사용하고 `TEST_F`를 우선 사용한다.

  - `quality == 50`
  - `sellIn == 0`
  - `sellIn == -1`
- 테스트 이름은 동작과 기대 결과가 명확히 드러나게 작성한다.

## 리팩토링 규칙
- 리팩토링은 테스트가 Green인 상태에서만 진행한다.
- 리팩토링 중에도 작은 단위로 변경하고 자주 테스트를 실행한다.
- 동작 변경과 구조 개선을 한 번에 섞지 않는다.
- 매직 넘버는 의미 있는 상수로 추출하는 것을 권장한다.
  - 예: `0`, `50`, 품질 증가/감소량, 특별 아이템 이름 등
- 중복 제거는 허용하되, Gilded Rose 규칙의 가독성을 해치지 않아야 한다.
- 레거시 코드의 특수 케이스를 제거하거나 일반화하기 전에 반드시 테스트로 보호한다.

## 코드 작성 기준
- 기존 코드 스타일과 파일 구조를 우선 따른다.
- 불필요한 추상화나 과도한 설계를 추가하지 않는다.
- 조건문을 정리할 때는 아이템별 비즈니스 규칙이 명확히 보이도록 한다.
- 주석은 복잡한 도메인 규칙을 설명할 때만 간결하게 작성한다.

## 작업 완료 기준
- 변경 후 관련 Google Test를 실행한다.
- 가능하면 전체 테스트도 실행한다.
- 테스트 실패가 있으면 리팩토링을 멈추고 원인을 먼저 해결한다.
