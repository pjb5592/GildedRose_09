# Gilded Rose 테스트 계획 보고서

작성일: 2026-05-19

## 1. 보고서 목적

본 보고서는 C++17, Google Test, CMake 기반 Gilded Rose 프로젝트의 테스트 전략을 정의한다.
목표는 `GildedRose::updateQuality()`의 핵심 비즈니스 규칙을 단위 테스트로 보호하고, 향후 리팩토링 및 `Conjured` 신규 요구사항 구현 시 회귀를 조기에 탐지하는 것이다.

테스트 대상은 다음 파일을 중심으로 한다.

- `cpp/include/GildedRose.h`
- `cpp/src/GildedRose.cpp`
- `GildedRoseRequirements.txt`
- `docs/requirements_analysis.md`

## 2. 현재 테스트 관점의 핵심 리스크

현재 구현은 Gilded Rose 레거시 코드 특성상 `updateQuality()` 내부에 아이템별 규칙이 중첩 조건문으로 섞여 있다.
따라서 작은 조건 변경도 여러 아이템 타입의 동작에 영향을 줄 수 있다.

주요 리스크는 다음과 같다.

- `Normal`, `Aged Brie`, `Backstage passes`, `Sulfuras` 규칙이 하나의 함수 안에 강하게 결합되어 있다.
- `quality` 하한 `0`과 상한 `50` 경계값이 여러 분기에서 반복적으로 다뤄진다.
- `sellIn == 0`은 호출 후 `sellIn == -1`이 되므로 판매 기한 경과 규칙이 즉시 적용된다.
- `Sulfuras`는 일반 품질 상한의 예외로 `quality == 80`을 유지해야 한다.
- 현재 구현에는 `Conjured` 신규 요구사항이 별도 규칙으로 반영되어 있지 않다.
- 테스트 파일을 분리할 경우 현재 `CMakeLists.txt`에 테스트 소스 등록이 추가로 필요하다.

## 3. 테스트 설계 원칙

단위 테스트는 Google Test의 `TEST_F`를 우선 사용한다.
공통 테스트 픽스처를 두어 아이템 생성, 하루 경과 실행, 결과 검증 흐름을 명확히 분리한다.

권장 테스트 픽스처 구조는 다음과 같다.

```cpp
class GildedRoseTest : public ::testing::Test {
protected:
    std::vector<Item> items;

    void AddItem(const std::string& name, int sellIn, int quality) {
        items.emplace_back(name, sellIn, quality);
    }

    void Update() {
        GildedRose app(items);
        app.updateQuality();
    }
};
```

테스트명은 `NormalItem_DecreasesQualityByOneBeforeSellDate`처럼 아이템 타입, 조건, 기대 결과가 드러나도록 작성한다.
각 테스트는 Given-When-Then 흐름을 유지하고, 하나의 테스트가 너무 많은 도메인 규칙을 동시에 검증하지 않도록 한다.

## 4. TEST_F 기반 단위 테스트 우선순위

| 우선순위 | 테스트 범위 | 검증 목적 |
|---|---|---|
| P0 | Normal 기본 감소, 기한 경과 후 2배 감소 | 가장 기본적인 품질 감소 규칙 보호 |
| P0 | `quality == 0`, `quality == 50` | 품질 하한·상한 보장 |
| P0 | `sellIn == 0`, `sellIn == -1` | 판매 기한 경계 처리 검증 |
| P0 | Aged Brie 증가 및 상한 | 증가형 아이템의 예외 규칙 보호 |
| P0 | Backstage passes 구간별 증가 및 공연 후 0 | 복합 분기 회귀 방지 |
| P0 | Sulfuras 불변 | 전설 아이템 예외 보호 |
| P1 | Conjured 품질 2배 감소 | 신규 요구사항 검증 |
| P1 | 여러 아이템 동시 처리 | 아이템 간 독립성 검증 |
| P2 | 빈 벡터, 비표준 이름, 동일 이름 중복 | 견고성 및 특이 입력 검증 |

## 5. 아이템별 필수 테스트 범위

### 5.1 Normal 아이템

- 판매 기한 전에는 하루가 지나면 `sellIn`이 `1` 감소하고 `quality`가 `1` 감소한다.
- 호출 전 `sellIn == 0`이면 호출 후 `quality`가 총 `2` 감소한다.
- 호출 전 `sellIn == -1`이면 이미 기한이 지난 상태로 보고 `quality`가 `2` 감소한다.
- `quality == 0`이면 더 이상 감소하지 않는다.
- `quality == 1`이고 감소량이 더 크더라도 결과는 `0`에서 멈춘다.

### 5.2 Aged Brie

- 판매 기한 전에는 `quality`가 `1` 증가한다.
- 호출 전 `sellIn == 0`이면 `quality`가 총 `2` 증가한다.
- 호출 전 `sellIn == -1`이면 `quality`가 `2` 증가한다.
- `quality == 49`에서 증가해도 `50`을 초과하지 않는다.
- `quality == 50`이면 더 이상 증가하지 않는다.

### 5.3 Backstage passes

- `sellIn > 10`이면 `quality`가 `1` 증가한다.
- `sellIn == 10`이면 `quality`가 `2` 증가한다.
- `sellIn == 5`이면 `quality`가 `3` 증가한다.
- 증가 후에도 `quality`는 `50`을 초과하지 않는다.
- 호출 전 `sellIn == 0`이면 콘서트 이후가 되어 `quality == 0`이 된다.
- 호출 전 `sellIn == -1`이면 계속 `quality == 0`을 유지한다.

### 5.4 Sulfuras

- 하루가 지나도 `sellIn`이 변경되지 않는다.
- 하루가 지나도 `quality == 80`을 유지한다.
- 호출 전 `sellIn == 0` 또는 `sellIn == -1`이어도 값이 변경되지 않는다.
- 일반 품질 상한 `50` 보정 로직의 영향을 받지 않는다.

### 5.5 Conjured

- 판매 기한 전에는 하루가 지나면 `quality`가 `2` 감소한다.
- 호출 전 `sellIn == 0`이면 `quality`가 총 `4` 감소한다.
- 호출 전 `sellIn == -1`이면 `quality`가 `4` 감소한다.
- `quality == 1` 또는 `quality == 0`에서 감소해도 음수가 되지 않는다.
- `"Conjured Mana Cake"`처럼 `"Conjured"` 접두어를 가진 아이템을 Conjured 계열로 볼지 테스트로 정책을 고정한다.

## 6. 경계값 케이스 목록

### 6.1 Quality 경계값

| 초기 quality | 대상 아이템 | 기대 결과 |
|---:|---|---|
| `0` | Normal, Conjured | 더 이상 감소하지 않는다 |
| `0` | Backstage passes | 콘서트 이후에도 `0` 유지 |
| `1` | Normal, Conjured | 감소량이 커도 `0` 미만으로 내려가지 않는다 |
| `49` | Aged Brie, Backstage passes | 증가 후 최대 `50`까지만 도달 |
| `50` | Aged Brie, Backstage passes | 더 이상 증가하지 않음 |
| `80` | Sulfuras | 전설 아이템 예외로 변경되지 않음 |

### 6.2 SellIn 경계값

| 초기 sellIn | 대상 아이템 | 기대 결과 |
|---:|---|---|
| `0` | Normal | 호출 후 기한 경과 규칙까지 반영되어 `quality` 총 `2` 감소 |
| `0` | Aged Brie | 호출 후 `quality` 총 `2` 증가 |
| `0` | Backstage passes | 호출 후 `quality == 0` |
| `0` | Sulfuras | `sellIn`과 `quality` 모두 불변 |
| `0` | Conjured | 호출 후 `quality` 총 `4` 감소 |
| `-1` | Normal | 이미 기한 경과 상태로 `quality` `2` 감소 |
| `-1` | Aged Brie | 이미 기한 경과 상태로 `quality` `2` 증가 |
| `-1` | Backstage passes | `quality == 0` 유지 |
| `-1` | Sulfuras | `sellIn`과 `quality` 모두 불변 |
| `-1` | Conjured | 이미 기한 경과 상태로 `quality` `4` 감소 |

### 6.3 Backstage 추가 경계값

| 초기 sellIn | 기대 증가량 |
|---:|---:|
| `11` | `+1` |
| `10` | `+2` |
| `5` | `+3` |
| `0` | `quality = 0` |

## 7. 예외 및 특이 케이스

테스트에서 반드시 분리해 검증해야 하는 예외 및 특이 케이스는 다음과 같다.

- `Sulfuras`는 `quality == 80`을 유지하며 일반 상한 `50`의 영향을 받지 않는다.
- `Sulfuras`는 `sellIn`도 감소하지 않는다.
- `Backstage passes`는 콘서트 이후 품질이 점진적으로 감소하는 것이 아니라 즉시 `0`이 된다.
- `sellIn` 음수는 오류가 아니며, 이미 판매 기한이 지난 상태를 의미한다.
- 빈 `items` 벡터는 예외 없이 처리되어야 한다.
- 여러 아이템을 한 번에 갱신해도 각 아이템은 독립적으로 처리되어야 한다.
- 특별 아이템 이름과 유사하지만 정확히 일치하지 않는 이름은 일반 아이템으로 처리되어야 한다.
- `Conjured` 이름 매칭 정책은 테스트로 명확히 고정해야 한다.

## 8. 커버리지 목표

테스트 커버리지 목표는 다음과 같이 설정한다.

- 라인 커버리지: `90%` 이상
- 함수 커버리지: `95%` 이상
- 브랜치 커버리지: `85%` 이상
- `GildedRose::updateQuality()` 핵심 분기 커버리지: 가능한 한 `100%`

본 프로젝트에서는 라인 커버리지보다 브랜치 커버리지를 더 중요하게 본다.
`updateQuality()`는 조건문이 많기 때문에 특정 라인이 실행되더라도 반대 조건이나 경계값이 검증되지 않을 수 있다.

## 9. gcov/lcov 측정 전략

GCC 또는 Clang의 gcov 호환 옵션을 사용해 커버리지를 측정한다.
권장 빌드 디렉터리는 `cpp/build-coverage`이다.

```bash
cd cpp
cmake -S . -B build-coverage -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS="--coverage -O0 -g" \
  -DCMAKE_EXE_LINKER_FLAGS="--coverage"
cmake --build build-coverage
ctest --test-dir build-coverage --output-on-failure
lcov --capture --directory build-coverage --output-file build-coverage/coverage.info
lcov --remove build-coverage/coverage.info '/usr/*' '*/_deps/*' '*/test/*' --output-file build-coverage/coverage.filtered.info
genhtml build-coverage/coverage.filtered.info --output-directory build-coverage/coverage-report
```

Windows 환경에서는 MinGW, MSYS2, WSL 중 실제 사용하는 GCC 계열 도구체인에 맞춰 실행한다.
MSVC만 사용하는 경우에는 OpenCppCoverage 같은 대체 도구 검토가 필요하다.

## 10. 커버리지 개선 절차

1. 먼저 P0 테스트를 작성해 기존 요구사항의 핵심 동작을 보호한다.
2. `ctest`로 전체 테스트가 Green인지 확인한다.
3. `lcov` HTML 리포트에서 `GildedRose.cpp`의 미실행 라인과 미충족 브랜치를 확인한다.
4. 누락된 분기를 아이템 타입별로 분류한다.
5. 누락 분기가 요구사항상 의미 있는 조건이면 경계값 테스트를 추가한다.
6. 리팩토링 후 동일한 테스트와 커버리지 측정을 반복한다.

우선 보강해야 할 분기는 다음과 같다.

- Normal 품질 감소 및 하한 분기
- Aged Brie 품질 증가 및 상한 분기
- Backstage passes `>10`, `<=10`, `<=5`, 공연 이후 분기
- Sulfuras 불변 분기
- Conjured 기본 감소, 기한 경과 후 감소, 하한 분기

## 11. 완료 기준

테스트 계획의 완료 기준은 다음과 같다.

- P0 테스트가 모두 Green이다.
- Conjured 구현 이후 P1 테스트가 모두 Green이다.
- `Item` 구조체와 `GildedRose::items` public 인터페이스가 변경되지 않았다.
- `GildedRose.cpp` 기준 라인 커버리지 `90%+`, 브랜치 커버리지 `85%+`를 달성했다.
- 커버리지 리포트에서 핵심 도메인 분기가 테스트 없이 남아 있지 않다.
- 리팩토링 전후 동일 테스트 스위트가 Green 상태를 유지한다.
