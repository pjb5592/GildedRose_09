# Gilded Rose 요구사항 구현 분석 보고서

작성일: 2026-05-19

## 1. 보고서 목적

본 보고서는 Gilded Rose C++17 프로젝트의 요구사항을 구현 관점에서 재정리한 문서이다.
대상 코드는 CMake와 Google Test 기반의 C++ 프로젝트이며, 핵심 검토 대상은 `GildedRose::updateQuality()`이다.

요구사항 분석의 초점은 다음과 같다.

- 아이템 타입별 `sellIn`, `quality` 변경 규칙 명확화
- C++ 문자열 비교 및 분기 구현 시 주의점 정리
- `quality`, `sellIn`, `Sulfuras` 관련 경계값과 예외 조건 식별
- 신규 `Conjured` 요구사항의 구현 기준 정의
- Google Test 기준 테스트 시나리오 도출

## 2. 아이템 타입별 비즈니스 규칙

| 아이템 타입 | 식별 기준 | `sellIn` 변경 | `quality` 변경 규칙 | 경계/예외 |
|---|---|---:|---|---|
| Normal | 특별 아이템명이 아닌 일반 아이템 | 매일 `-1` | 판매 기한 전 `-1`, 기한 경과 후 `-2` | `quality`는 `0` 미만 불가 |
| Aged Brie | `name == "Aged Brie"` | 매일 `-1` | 판매 기한 전 `+1`, 기한 경과 후 `+2` | `quality`는 `50` 초과 불가 |
| Backstage Pass | `name == "Backstage passes to a TAFKAL80ETC concert"` | 매일 `-1` | `sellIn > 10`: `+1`<br>`6 <= sellIn <= 10`: `+2`<br>`1 <= sellIn <= 5`: `+3`<br>콘서트 이후: `0` | 증가 중 `quality`는 `50` 초과 불가 |
| Sulfuras | `name == "Sulfuras, Hand of Ragnaros"` | 변경 없음 | 변경 없음 | 전설 아이템. `quality == 80` 유지 |
| Conjured | `"Conjured"` 계열 아이템 | 매일 `-1` | 판매 기한 전 `-2`, 기한 경과 후 `-4` | `quality`는 `0` 미만 불가 |

구현 시 `Sulfuras`는 가장 먼저 처리하거나 별도 분기로 제외하는 것이 안전하다. `Sulfuras`는 `sellIn`과 `quality`가 모두 변하지 않으므로 일반적인 품질 보정 로직도 적용하지 않아야 한다.

## 3. C++ 문자열 비교 및 분기 주의점

1. 고정된 특별 아이템명은 `std::string::operator==`로 비교한다.
   - `"Aged Brie"`
   - `"Backstage passes to a TAFKAL80ETC concert"`
   - `"Sulfuras, Hand of Ragnaros"`

2. `std::string::find()`는 조건식에 직접 사용하지 않는다.
   - `find()`는 발견 위치 또는 `std::string::npos`를 반환한다.
   - 문자열 맨 앞에서 발견되면 반환값이 `0`이므로 조건식에서 `false`처럼 해석될 수 있다.
   - 찾지 못한 경우 `npos`는 큰 정수이므로 조건식에서 `true`처럼 해석될 수 있다.

3. `find()`를 사용할 때는 반드시 `std::string::npos`와 비교한다.

   ```cpp
   if (item.name.find("Conjured") != std::string::npos) {
       // Conjured 계열 아이템 처리
   }
   ```

4. C++17에는 `std::string::starts_with()`가 없다.
   - 접두어 기준으로 `Conjured` 계열을 식별하려면 `item.name.rfind("Conjured", 0) == 0`를 사용할 수 있다.
   - 포함 기준인지 접두어 기준인지는 테스트로 명확히 고정해야 한다.

5. 분기 순서는 예외 규칙이 많은 아이템을 먼저 고려한다.
   - 권장 순서: `Sulfuras` → `Backstage Pass` → `Aged Brie` → `Conjured` → Normal
   - 이렇게 하면 전설 아이템 예외와 신규 `Conjured` 감소 규칙이 일반 아이템 처리에 섞이는 위험을 줄일 수 있다.

## 4. 예외 및 경계값 조건

1. `quality == 0`
   - Normal과 Conjured는 더 이상 감소하지 않아야 한다.
   - 감소량이 현재 `quality`보다 큰 경우에도 결과는 `0`이어야 한다.

2. `quality == 50`
   - Aged Brie와 Backstage Pass는 더 이상 증가하지 않아야 한다.
   - 증가량이 `+2` 또는 `+3`이어도 결과는 `50`을 초과하면 안 된다.

3. `Sulfuras quality == 80`
   - `Sulfuras`는 일반 품질 상한인 `50`의 예외다.
   - `quality` 보정 함수가 있다면 `Sulfuras`에는 적용하지 않아야 한다.

4. `sellIn == 0`
   - 하루가 지나면 `sellIn == -1`이 된다.
   - Normal은 총 `2` 감소, Aged Brie는 총 `2` 증가, Conjured는 총 `4` 감소해야 한다.
   - Backstage Pass는 콘서트 이후 상태가 되므로 `quality == 0`이 되어야 한다.

5. `sellIn == -1` 및 음수 값
   - 음수 `sellIn`은 오류가 아니라 판매 기한이 지난 상태다.
   - Normal, Aged Brie, Conjured는 기한 경과 후 규칙을 계속 적용한다.
   - Backstage Pass는 계속 `quality == 0`을 유지해야 한다.

## 5. Conjured 신규 요구사항

`Conjured` 아이템은 일반 아이템보다 2배 빠르게 품질이 감소하는 신규 카테고리다.

명세는 다음과 같이 고정하는 것을 권장한다.

1. 판매 기한 전에는 하루에 `quality`가 `2` 감소한다.
2. 판매 기한이 지난 뒤에는 하루에 `quality`가 `4` 감소한다.
3. `quality`는 `0` 미만으로 내려가지 않는다.
4. `sellIn`은 일반 아이템과 동일하게 매일 `1` 감소한다.
5. `"Conjured Mana Cake"` 같은 계열 아이템을 지원하려면 접두어 매칭 정책을 테스트로 고정한다.

## 6. Google Test 테스트 시나리오

1. Normal 아이템은 하루가 지나면 `sellIn`이 `1` 감소하고 `quality`가 `1` 감소한다.
2. Normal 아이템은 `sellIn == 0`에서 업데이트하면 `quality`가 총 `2` 감소한다.
3. Normal 아이템은 `sellIn < 0`에서 업데이트하면 `quality`가 `2` 감소한다.
4. Normal 아이템은 `quality == 0`에서 더 감소하지 않는다.
5. Aged Brie는 하루가 지나면 `quality`가 `1` 증가한다.
6. Aged Brie는 `sellIn == 0`에서 업데이트하면 `quality`가 총 `2` 증가한다.
7. Aged Brie는 `sellIn < 0`에서 업데이트하면 `quality`가 `2` 증가한다.
8. Aged Brie는 `quality == 50`에서 더 증가하지 않는다.
9. Backstage Pass는 `sellIn > 10`일 때 `quality`가 `1` 증가한다.
10. Backstage Pass는 `sellIn == 10`일 때 `quality`가 `2` 증가한다.
11. Backstage Pass는 `sellIn == 5`일 때 `quality`가 `3` 증가한다.
12. Backstage Pass는 증가 후에도 `quality`가 `50`을 초과하지 않는다.
13. Backstage Pass는 `sellIn == 0`에서 업데이트하면 `quality`가 `0`이 된다.
14. Backstage Pass는 `sellIn < 0`에서 업데이트해도 `quality`가 `0`으로 유지된다.
15. Sulfuras는 업데이트 후에도 `sellIn`이 변경되지 않는다.
16. Sulfuras는 업데이트 후에도 `quality == 80`을 유지한다.
17. Sulfuras는 일반 품질 상한 보정 로직의 영향을 받지 않는다.
18. Conjured 아이템은 판매 기한 전 하루가 지나면 `quality`가 `2` 감소한다.
19. Conjured 아이템은 `sellIn == 0`에서 업데이트하면 `quality`가 총 `4` 감소한다.
20. Conjured 아이템은 `sellIn < 0`에서 업데이트하면 `quality`가 `4` 감소한다.
21. Conjured 아이템은 감소량이 현재 `quality`보다 커도 `quality == 0`에서 멈춘다.
22. Conjured 이름 매칭 정책을 검증한다.
23. 여러 아이템이 동시에 있을 때 각 아이템이 독립적으로 갱신된다.
24. 빈 아이템 벡터를 전달해도 예외 없이 처리된다.

## 7. QA 관점 리스크

- `sellIn` 감소 전후 기준을 혼동하면 `sellIn == 0` 경계에서 기대 결과가 달라질 수 있다.
- `std::string::find()`를 잘못 사용하면 `Conjured` 식별 조건이 반대로 동작할 수 있다.
- `Sulfuras`에 일반 품질 보정 로직을 적용하면 `quality == 80` 불변 조건이 깨질 수 있다.
- Conjured의 기한 경과 후 감소량을 `-2`로만 구현하면 신규 요구사항의 "2배 감소" 해석이 누락된다.
- 테스트 없이 중첩 조건문을 리팩토링하면 기존 레거시 동작이 변경될 가능성이 높다.

## 8. 결론

현재 요구사항은 아이템 타입별 예외가 많으므로, 구현보다 먼저 명세 테스트를 충분히 확보하는 것이 중요하다.
특히 `quality == 0`, `quality == 50`, `sellIn == 0`, `sellIn < 0`, `Sulfuras quality == 80`, `Conjured` 감소율은 필수 테스트 대상이다.

리팩토링은 `Item` 인터페이스를 변경하지 않고, `updateQuality()` 내부의 아이템 분류와 품질 증감 로직을 명확히 분리하는 방향으로 진행하는 것이 적절하다.
