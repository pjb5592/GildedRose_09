# Gilded Rose QA 및 리팩토링 보고서

작성일: 2026-05-19

## 1. 프로젝트 개요

본 프로젝트는 C++17, CMake, Google Test 기반의 Gilded Rose 레거시 코드 실습 프로젝트이다.
핵심 구현 대상은 `GildedRose::updateQuality()`이며, 아이템의 `sellIn`과 `quality`를 하루 단위로 갱신한다.

주요 도메인 규칙은 다음과 같다.

- 일반 아이템은 하루가 지나면 `quality`가 1 감소한다.
- 판매 기한이 지난 일반 아이템은 `quality`가 2 감소한다.
- `Aged Brie`는 시간이 지날수록 `quality`가 증가한다.
- `Backstage passes`는 공연일이 가까워질수록 `quality` 증가량이 커지고, 공연일 이후에는 0이 된다.
- `Sulfuras`는 전설 아이템이므로 `sellIn`과 `quality`가 변하지 않는다.
- `Conjured` 아이템은 일반 아이템보다 2배 빠르게 품질이 감소해야 한다.

## 2. 절대 준수 규칙

- `Item` 클래스의 필드, 생성자, public 인터페이스는 수정하지 않는다.
- `quality`는 일반 아이템 기준으로 0 이상 50 이하를 유지해야 한다.
- `Sulfuras`는 예외적으로 `quality` 80을 가질 수 있으며 값이 변하지 않아야 한다.
- `sellIn`은 음수가 될 수 있으므로 음수 값을 오류로 처리하지 않는다.
- 리팩토링은 테스트가 Green인 상태에서만 진행한다.

## 3. 현재 코드 상태

현재 `GildedRose.cpp`의 `updateQuality()`는 중첩 조건문 중심으로 구현되어 있다.
기존 Gilded Rose 레거시 코드 형태에 가깝기 때문에 동작 파악은 가능하지만, 다음 문제가 있다.

- 아이템 이름 문자열이 여러 조건문에 직접 반복된다.
- `0`, `50`, `11`, `6` 등의 매직 넘버가 직접 사용된다.
- 일반 아이템, `Aged Brie`, `Backstage passes`, `Sulfuras` 규칙이 하나의 함수에 섞여 있다.
- 신규 요구사항인 `Conjured` 아이템 규칙은 아직 구현되어 있지 않다.
- 현재 테스트가 충분하지 않아 리팩토링 안전망이 부족하다.

## 4. 현재 테스트 상태

현재 `cpp/test/GildedRoseTest.cpp`에는 기본 실패 테스트가 남아 있다.

```cpp
TEST(GildedRoseTest, Foo) {
    std::vector<Item> items = { Item("foo", 0, 0) };
    GildedRose app(items);
    app.updateQuality();
    EXPECT_EQ("fixme", app.items[0].name);
}
```

실행 결과:

- 빌드: 성공
- 테스트: 실패
- 실패 테스트: `GildedRoseTest.Foo`
- 실패 원인: 기대값 `"fixme"`와 실제 아이템 이름 `"foo"`가 다름

따라서 현재 상태에서는 리팩토링을 진행하기 전에 테스트를 의미 있는 명세 테스트로 교체해야 한다.

## 5. 테스트 보강 권장사항

테스트는 Google Test 기반으로 작성하고, Given-When-Then 흐름이 드러나도록 구성한다.
관련 테스트 픽스처를 정의한 뒤 `TEST_F` 사용을 우선 권장한다.

우선 보강해야 할 경계값은 다음과 같다.

- `quality == 0`: 품질이 음수가 되지 않는지 확인
- `quality == 50`: 품질이 50을 초과하지 않는지 확인
- `sellIn == 0`: 판매 기한 당일 처리 확인
- `sellIn == -1`: 판매 기한 경과 후 처리 확인

아이템별 필수 테스트 범위는 다음과 같다.

- 일반 아이템: 기본 감소, 기한 경과 후 2배 감소, 품질 하한 0
- `Aged Brie`: 기본 증가, 기한 경과 후 2배 증가, 품질 상한 50
- `Backstage passes`: 11일 이상, 10일 이하, 5일 이하, 공연일 이후 0
- `Sulfuras`: `sellIn`과 `quality` 불변
- `Conjured`: 일반 아이템보다 2배 빠른 감소, 기한 경과 후 감소량 확인, 품질 하한 0

## 6. 리팩토링 권장 순서

1. 현재 실패 테스트를 실제 요구사항 기반 테스트로 교체한다.
2. 일반 아이템, 특수 아이템, 경계값 테스트를 추가해 Green 상태를 만든다.
3. 아이템 이름과 품질 경계값을 상수로 추출한다.
4. 품질 증가/감소 로직을 작은 헬퍼 함수로 분리한다.
5. 아이템별 처리 흐름을 명확히 분리한다.
6. 모든 테스트가 Green인 상태에서 `Conjured` 규칙을 추가한다.
7. gcov/lcov를 통해 핵심 분기 커버리지를 확인한다.

## 7. 주요 리스크

- 테스트가 부족한 상태에서 조건문을 정리하면 기존 레거시 동작이 바뀔 수 있다.
- `sellIn` 감소 전후 기준을 잘못 해석하면 `Backstage passes`와 기한 경과 규칙이 깨질 수 있다.
- `Sulfuras` 예외 처리를 일반 품질 경계 규칙과 섞으면 `quality` 80 불변 조건이 손상될 수 있다.
- `Conjured` 구현 시 기한 경과 후 감소량을 명확히 테스트하지 않으면 요구사항 해석 차이가 발생할 수 있다.

## 8. 결론

현재 프로젝트는 빌드는 가능하지만 기본 테스트가 실패하고 있어 리팩토링을 시작하기에는 안전망이 부족하다.
우선 Google Test 기반의 명세 테스트를 작성해 Green 상태를 만든 뒤, 매직 넘버 상수화와 아이템별 로직 분리를 단계적으로 진행하는 것이 적절하다.

`.cursorrules`에 정의한 프로젝트 규칙을 기준으로, `Item` 클래스는 수정하지 않고 테스트 Green 상태를 유지하면서 작은 단위로 리팩토링해야 한다.
