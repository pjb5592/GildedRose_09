# Gilded Rose `updateQuality()` 리팩토링 계획 보고서

작성일: 2026-05-19

## 1. 보고서 목적

본 보고서는 C++17 Gilded Rose 프로젝트에서 `GildedRose::updateQuality()`에 대한 **모던 C++ 리팩토링 로드맵**을 정리한다.

목표는 다음과 같다.

- 조건 분기 축소 및 중복 제거 (커밋 단위 점진 적용)
- 아이템별 품질 정책 분리 (함수 분해 → 분류 → 테이블/전략 디스패치)
- 매직 넘버 상수화 및 C++17 스타일 정리
- **동작 변경 없이** 테스트 Green 상태를 유지한 채 구조만 개선

## 2. 절대 제약

| 제약 | 내용 |
|------|------|
| `Item` 구조체 | 필드, 생성자, public 인터페이스 수정 금지 |
| 품질 범위 | 일반 아이템 `0 <= quality <= 50` |
| `Sulfuras` | `quality`·`sellIn` 변경 없음, clamp 미적용 |
| `sellIn` | 음수 허용 (오류 아님) |
| 리팩토링 진행 | 각 커밋 후 `cmake --build` + `ctest` Green 필수 |

## 3. 현재 코드 기준선 (Baseline)

`cpp/src/GildedRose.cpp`는 레거시(중첩 `if`, 인덱스 접근, 인라인 `0`/`50`) 대비 이미 1차 정리가 완료된 상태이다.

| 항목 | 상태 |
|------|------|
| `kMinimumQuality` / `kMaximumQuality` | 완료 |
| 특수 아이템 이름 `constexpr` | 완료 |
| `increaseQuality` / `decreaseQuality` 헬퍼 | 완료 |
| 범위 기반 `for (Item& item : items)` | 완료 |
| `Sulfuras` 조기 `continue` | 완료 |
| `originalSellIn` 기반 만료 판정 | 완료 |
| Conjured 접두어 `rfind(..., 0) == 0` | 완료 |

### 3.1 현재 `updateQuality()` 구조 요약

1. `Sulfuras` → `continue` (변경 없음)
2. `originalSellIn` 저장 → `sellIn -= 1`
3. 이름/접두어 분기: Aged Brie / Backstage / Conjured / Normal
4. 품질 변경은 헬퍼로 clamp

### 3.2 테스트 안전망

| 구분 | 수량 | 비고 |
|------|------|------|
| 단위 테스트 (`GildedRoseTest.cpp`) | 27개 | Given-When-Then, 경계값 포함 |
| Golden Master | 1개 | 31일 Texttest 출력 전체 비교 |
| 검증 명령 | `cmake --build cpp/build` + `ctest --test-dir cpp/build` | |

## 4. 남은 품질 이슈 (문서 대비)

`docs/code_quality_report.md` 기준으로 아직 개선 여지가 있는 항목:

- Backstage 임계값 `5`, `10` 및 증가량 `1`/`2`/`3`의 명시적 상수화
- 아이템별 정책 함수 미분리 (SRP)
- 문자열 비교가 `updateQuality()` 루프에 분산
- OCP: 신규 타입 추가 시 분기 확장 필요

## 5. 단계별 리팩토링 계획

### Phase 0 — 기준선 고정 (선택, 커밋 0)

| 체크 | 작업 |
|------|------|
| ☐ | 전체 `ctest` Green 확인 |
| ☐ | (선택) `git tag refactor-baseline` |

**검증:** `gilded_rose_test` + `gilded_rose_golden_test` PASS.

---

### Phase 1 — 매직 넘버·도메인 상수 (커밋 1)

**목적:** Backstage 임계일·품질 증감량을 이름 있는 상수로 표현.

```cpp
constexpr int kBackstageDoubleThreshold = 10;
constexpr int kBackstageTripleThreshold = 5;
constexpr int kQualityDeltaBeforeExpiry = 1;
constexpr int kQualityDeltaAfterExpiry = 2;
constexpr int kConjuredMultiplier = 2;
```

| 체크 | 검증 |
|------|------|
| ☐ | 로직·분기 순서 동일 | `ctest -R BackstagePass` |
| ☐ | sellIn==10 → +2, sellIn==5 → +3 | |

**커밋 예:** `refactor: name backstage thresholds and quality deltas`

---

### Phase 2 — 하루 경과 템플릿 (커밋 2)

**목적:** `sellIn` 감소 + `originalSellIn` 패턴을 `applyDailyUpdate()`로 고정.

| 체크 | 검증 |
|------|------|
| ☐ | Sulfuras는 템플릿 미호출 | |
| ☐ | 품질 갱신 전 `sellIn` 1회만 감소 | Golden Master PASS |

**커밋 예:** `refactor: extract daily sellIn decrement template`

---

### Phase 3 — 아이템별 정책 함수 (커밋 3a~3d)

| 커밋 | 함수 | 책임 |
|------|------|------|
| 3a | `updateNormalQuality` | 감소 1/2 |
| 3b | `updateAgedBrieQuality` | 증가 1/2 |
| 3c | `updateBackstagePassQuality` | 만료 0 / +1~+3 |
| 3d | `updateConjuredQuality` | 2× 감소 |

Backstage 만료 시 `quality = 0`은 **대입**으로 유지 (`decreaseQuality` 사용 금지).

| 단계 | ctest 필터 |
|------|------------|
| 3a | `-R NormalItem` |
| 3b | `-R AgedBrie` |
| 3c | `-R BackstagePass` |
| 3d | `-R Conjured` |

---

### Phase 4 — `ItemKind` 분류 (커밋 6)

```cpp
enum class ItemKind { Normal, AgedBrie, BackstagePass, Sulfuras, Conjured };
ItemKind classifyItem(const Item& item);
```

`switch (classifyItem(item))`로 문자열 비교를 한 곳에 모음. `Item` 구조체는 변경하지 않음.

**검증:** `ConjuredPrefixNameUsesConjuredRules` PASS.

---

### Phase 5 — 디스패치 (커밋 7, 택1)

| 옵션 | 적합 상황 |
|------|-----------|
| **A. 함수 테이블** | 아이템 종류 ≤5, 과설계 방지 (권장) |
| **B. 전략 패턴** | 신규 타입 반복 추가 시 OCP 강화 |

**검증:** 전체 unit + golden PASS, `updateQuality()` 15줄 내외.

---

### Phase 6 — C++17 마무리 (선택, 커밋 8)

- `std::string_view` 상수 비교
- `[[nodiscard]]` on `classifyItem`
- `std::clamp`는 Sulfuras/Backstage 만료 경로와 혼동 가능 → 기존 `min`/`max` 헬퍼 유지 권장

**금지:** `Item` 필드 변경, C++20 `starts_with`.

## 8. 설계 결정 메모

1. **`originalSellIn` 유지:** 감소 전 `sellIn`으로 만료 규칙을 판정한다. Phase 2~3에서 `sellInBeforeUpdate`로 이름 통일 권장.
2. **Backstage 만료:** `quality = 0`은 delta 함수가 아닌 별도 분기.
3. **테스트 우선:** 27개 단위 + Golden Master로 요구사항 고정. 리팩토링 중 신규 테스트는 동작 변경·버그 수정 시에만.
4. **파일 분리:** 150줄 초과 시 `ItemPolicies.cpp` 검토, public API는 `GildedRose.h` 최소 유지.
